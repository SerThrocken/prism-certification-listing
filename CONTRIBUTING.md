## What you can contribute, and how

### A result file (self-tested row)

Run the published kit against your pack, sign the result file with your author key, and open a pull request adding **only** the result file under `results/<runtime>/<pack_id>/<suite>/`. The listing files (`listing.md`, `listing.json`) are generated, never hand-edited — a PR that edits them is closed and regenerated by the maintainer instead. Your row lists when the result file carries a complete environment card and its suite hash matches the frozen suite; a case run against local-only fixtures must carry its *bench-reproducible only* marking.

### A witness co-signature

Run a kit, keep copies of the checkpoints you have seen, and co-sign them under `checkpoints/witnesses/` per the format in `checkpoints/`. Witnessing is the cheapest high-value contribution in this project: it is what makes the history rewrite-evident (§11.8).

### An attack pack or a break report

See [SECURITY.md](SECURITY.md). Attack packs are submitted under `attacks/<claim_id>/` with a plain-words description of what the pack does and the result expected if it succeeds. A successful break of a listed claim is published with your name on it and the claim revoked with your attack cited (§11.9).

### A change to a frozen suite — the §11.1 process, no shortcuts

Whoever controls the tests controls the truth, so suite changes follow the strongest process in this project. There is no lighter path, for anyone, including the founder:

1. **Public proposal** — a file in `proposals/` (via a `proposal/<slug>` branch / PR) stating what changes (a case added, removed, weakened, or re-scored) and **why**.
2. **Comment window of at least 14 days** — the PR stays open and unmerged for the full window, whatever the early comments say.
3. **Threshold sign-off, 2 of 3** — the bench key set (§11.3) signs off, recorded as a signed commit. The change, its reason, and its signatories are part of the public record permanently.

A suite change never applies retroactively: results listed before it are marked historical (§4.6). The same full process — proposal, 14 days, threshold sign-off, **without exception** — governs any change that would move a feature inside the trusted core (the verifier's scorer, the negotiation check, the run-record writer; §11.10).

### An implementation

A second independent implementation of a spec feature is how a feature stops being a product feature and becomes a standard (§11.7). If two honest implementations disagree on steps, outcomes, or scores for the same pack, the disagreement is published as a finding (§11.11) — file it as an issue with both run records attached, shared form only (hashes, never payloads; §5.3).

## Rules that apply to every contribution

- **Attribution survives.** Author and licence fields on any pack, suite, or result are carried unchanged (§2.3). Stripping or altering them fails the kit's checks and voids certification.
- **Shared form only.** Never commit payloads, free-text run notes, credentials, keys, or local-only fixtures. Result and record files carry hashes and templated summaries (§5.3). The pre-publication secrets sweep runs on exports; a contribution that trips it is rejected, not edited around.
- **No claim wording violations.** Contributions, rows, and docs may not claim any system is unbreakable, unhackable, or compromise-proof (§11). The claim this project makes is compromise-*evident*: visible in the record, and revocable.
- **History is append-only.** Results are superseded or revoked by new commits naming the reason, never quietly edited (§4.6).
